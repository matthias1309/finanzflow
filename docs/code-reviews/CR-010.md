## Summary

Fixes a reported bug: two accounts each holding a `transfer` transaction to the other in the same
month (e.g. sweeping money back and forth between a Tagesgeldkonto and a Hauptkonto) produced two
opposing `transfersOut` entries between the same account pair. The Sankey diagram lays these out
as account-node links via `d3-sankey`, which requires a directed acyclic graph — the 2-node cycle
made it throw `Error("circular link")` inside `SankeyChart`'s `useEffect`, uncaught, which unmounts
the whole React tree and leaves a blank page.

Two changes, both TDD (failing tests written and confirmed red before implementation):

1. `server/routes/summary.ts`'s `buildAccountSummaries` now nets opposing `transfersOut` entries
   between the same two accounts to a single net-direction flow (AC-004-13), removing the cycle at
   its source and better reflecting reality (two opposite transfers are, net, one movement).
2. A new `ChartErrorBoundary` (`client/src/components/ChartErrorBoundary.tsx`) wraps `SankeyChart`
   in `Dashboard.tsx` as defense in depth (AC-009-08) — any remaining chart-rendering error (e.g. a
   3+-account transfer cycle, which the pairwise netting above doesn't cover) now shows a fallback
   message in the chart's card instead of crashing the rest of the Dashboard.

### Notes

- The E2E test for AC-009-08 (`TC-009-08`) could not be executed end-to-end in this session due to
  the two environment issues above (Findings #1 and #2), both pre-existing and unrelated to this
  change. Correctness of `ChartErrorBoundary` rests on: (a) it being a standard, minimal React
  error-boundary implementation (`getDerivedStateFromError`/`componentDidCatch`, no custom logic
  beyond rendering a fallback), and (b) a live-browser trace captured *before* this fix existed,
  which reproduced the exact reported bug (blank page, no elements) when a 2-account reciprocal
  transfer reached the unfixed `SankeyChart` — confirming the diagnosis this component addresses.
- Netting is intentionally scoped to the reported 2-account case (see ARCH-004 Key Decisions). A
  3+-account transfer cycle is a known, accepted gap covered only by the error boundary, not by
  data-level prevention — flagged in REQ-004's Notes and ARCH-004's Key Decisions for future
  reference, not treated as this session's problem to solve (YAGNI: no such case has been
  reported).
