# CR-008 — Env-sync no longer overwrites an existing user's password

**Status:** approved
**Created:** 2026-09-25
**Reviewer:** Claude Code (self-review, single-developer project)
**Traces:** REQ-015
**Covers:** ARCH-015, TEST-015

---

## Summary

Bug fix: `server/db.ts`'s startup ENV-sync unconditionally overwrote the `APP_USER` row's
`password_hash` with `APP_PASSWORD_HASH` on every server start, even when the user already
existed. Reported symptom: a password set for the admin user via `/users` (`PATCH
/api/users/:id/password`) appeared to "not stick" — it worked until the next restart, then was
silently reverted to the value baked into `APP_PASSWORD_HASH`.

Fix restricts `APP_PASSWORD_HASH` to the create path only; an existing user's password hash is
never touched by the seed again (`isAdmin = 1` is still re-asserted on every start). Updated
REQ-015 (AC-015-15), ARCH-015, TEST-015 (TC-015-15), added ADR-010 in `ARC42.md`, and flipped the
assertion in `tests/server/unit/db-seeding.test.ts`.

Files changed: `server/db.ts`, `docs/requirements/REQ-015.md`, `docs/architecture/ARCH-015.md`,
`docs/architecture/ARC42.md`, `docs/test-specs/TEST-015.md`,
`tests/server/unit/db-seeding.test.ts`, `CHANGELOG.md`.

### Notes

Reported by the user as "cannot set the admin password through the UI." Root cause was the
ENV-sync in `server/db.ts` reverting the change on the next restart rather than the
`PATCH /api/users/:id/password` endpoint itself, which worked correctly. Three fix strategies were
discussed with the developer (seed-once-only, a `passwordManagedByEnv` flag column, removing the
sync entirely); "seed-once-only" was chosen as the smallest change that removes the surprising
behavior while keeping `APP_PASSWORD_HASH` as the documented way to provision the very first admin
account.

Follow-up not in scope here: `docs/requirements/REQ-015.md` Notes already flags a separate,
pre-existing gap — `PATCH /api/users/:id/password` has no ownership check, so any authenticated
user can currently change *any* other user's password (tracked as a `known issue:` regression test
in `tests/server/api/users.test.ts`). Untouched by this fix.
