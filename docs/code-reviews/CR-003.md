## Summary

Review of the Session 7 V-Model retrofit (`docs/MIGRATION-PLAN.md`) for REQ-005 (PDF bank
statement import), REQ-006 (automatic category suggestion / learning), and REQ-011 (batch
transaction import). Scope: the new ARCH/TEST-SPEC documents, the `// TC-NNN-YY` comments added to

REQ-006's ACs — one implementation gap confirmed by a direct, throwaway test (not merged, run and
discarded during this review).

This session also surfaced, by simple inspection rather than a bug, the largest **test-coverage**
gap found in the migration so far: `POST /api/import/pdf` and the entire category-learning system
(`storage.suggestCategory`, `storage.learnCategoryRules`, `categoryRulesRouter`) have zero test
coverage — no unit test, no API test. `tests/server/unit/pdfParser.test.ts` only covers three pure
helper functions (`parseGermanAmount`, `parseGermanDate`, `detectBank`); the actual bank-specific
line parsers (`parseN26`, `parseDKB`, `parseGeneric`) and the upload route itself are untested.

Docs-only retrofit (no application code changed; per D7, a CR is not required to merge Session 7's
own PR). This CR exists for the same reason CR-001/CR-002 did.

## Findings

_Both findings are pre-existing behavior in already-shipped code (not introduced by this PR),
surfaced while writing ARCH-011 against REQ-006/REQ-011's ACs. Neither is a regression from
Session 7's own changes — Session 7 changed no application code._

| # | Severity | File / Line | Description |
|---|----------|-------------|-------------|
| 1 | **major** | `server/routes/categoryRules.ts:26-33` (`POST /learn`) | `learnBatchSchema.safeParse(req.body)` validates the whole array in one call — Zod fails the entire parse if *any* item fails its per-entry schema. **Confirmed by direct test** (run during this review, not committed): a batch `[{valid}, {categoryId: -5}]` returns `400` for the whole request; the valid entry is never saved. Contradicts AC-006-08 and AC-011-06 ("invalid entries are skipped, valid ones still processed"). `transactionsRouter.post("/batch")` in the neighboring `transactions.ts` already implements the correct pattern — per-item `safeParse`, filter valid from invalid, save the valid ones, report the rest — so the fix is a known, local pattern to copy, not new design work. |
| 2 | **minor** | `server/routes/categoryRules.ts` (no rate limiter), REQ-011 Notes | REQ-011's Notes state both batch endpoints "share the same 20-requests/15-min rate limit per IP." Only `POST /api/transactions/batch` has `batchRateLimiter` applied; `POST /api/category-rules/learn` has none (it only inherits the app-wide `authRateLimiter`, a materially different, failure-counting limiter). Lower severity than Finding 1 because it's an availability/abuse-prevention gap, not a data-integrity one, and the endpoint is behind `requireAuth` already (single-household deployment, not internet-exposed to anonymous callers). |

Both findings, plus 21 lower-severity missing-test items (the bulk of them "zero coverage" rather
than "found a bug"), are catalogued in the Test Gap Backlog of `docs/MIGRATION-PLAN.md` and in
`docs/architecture/ARCH-011.md` ("Open Questions").

## Decision

- [x] **Approved with minor fixes** — the *docs-only* Session 7 PR (ARCH/TEST-SPEC + TC comments) is ready to merge as-is; nothing in it needs to change
- [x] **Needs changes** — Finding 1 is a genuine correctness gap that silently defeats the
  documented partial-success contract of the learn endpoint and should be fixed (mirror the
  existing per-item pattern from `transactions.ts`) before REQ-006/REQ-011 can be considered
  reviewed and closed; Finding 2 is lower priority but cheap to fix alongside it (add
  `batchRateLimiter` to the `/learn` route, or correct the REQ-011 Notes if the asymmetry is
  actually intentional)

### Notes

- Same pattern as CR-001/CR-002: both decision boxes are checked because the documentation PR can
  merge independently of findings that live in code this PR does not touch.
- Recommended fix, when picked up: change `categoryRulesRouter.post("/learn")` to map each entry
  through `learnEntrySchema.safeParse` individually (same shape as
  `transactionsRouter.post("/batch")`), collect `valid`/`invalid` separately, call
  `storage.learnCategoryRules(valid)`, and return `{ learned, skipped, errors }` instead of the
  current `{ learned }`. Add regression test `TC-006-08` ("invalid entries are skipped, valid ones
  are still learned") alongside the fix.
- Unlike CR-002's Finding 1 (a negative `amount` silently corrupting a KPI total), this session's
  Finding 1 fails *loudly* (a `400` the user would see) but *incompletely* — the user loses the
  entire batch's learning instead of just the one bad entry, which is a worse user experience than
  a data-integrity risk. Recommended before Session 10 given it's user-visible, but lower urgency
  than CR-001's session-invalidation gap or CR-002's amount-positivity gap.
- The most valuable single deliverable from Session 10 for this REQ trio would be establishing
  *any* baseline coverage for `POST /api/import/pdf` and the learning system — right now a
  regression in either would ship completely undetected by `npm test`.
- Once Finding 1 is fixed, update this CR's Decision to **Approved**.
