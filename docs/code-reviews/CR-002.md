## Findings

_Both findings are pre-existing behavior in already-shipped code (not introduced by this PR),
surfaced while writing ARCH-004 against REQ-004's ACs. Neither is a regression from Session 6's
own changes — Session 6 changed no application code._

| # | Severity | File / Line | Description |
|---|----------|-------------|-------------|
| 1 | **major** | `shared/schema.ts:153` (`insertTransactionSchema`), `server/routes/transactions.ts:41` (`POST /`) | `amount` has no positivity refinement — only `type` is `.extend()`-ed onto the base Drizzle column. **Confirmed by direct test** (run during this review, not committed): `POST /api/transactions` with `amount: -50` returns `201`. Violates AC-004-09 and the project-wide invariant in `architecture.md` ("amount in the DB is always positive; type carries the sign semantics"). A negative amount on an `"income"` row would silently *subtract* from `totalIncome` in `server/routes/summary.ts` instead of being rejected — the aggregation code has no independent guard, it trusts the (currently unenforced) schema invariant. |
| 2 | **minor** | `shared/schema.ts` (`insertTransactionSchema`), `server/routes/summary.ts:82-87` | AC-004-06 ("transfer requires a target account") has no server-side refinement — `POST /api/transactions` accepts `{ type: "transfer", transferToAccountId: null }`. `buildAccountSummaries`'s `if (tx.type === "transfer" && tx.transferToAccountId)` guard then silently excludes such a row from *both* the source's `transfersOut` and any target's `transfersIn` — the amount just disappears from all account balances rather than erroring. Lower severity than Finding 1 because it fails safe (money isn't double-counted or misclassified, it's dropped and would show as an unexplained balance discrepancy the user would likely notice), but still a missing validation. |

Both findings, plus 19 lower-severity missing-test items, are catalogued in the Test Gap Backlog
of `docs/MIGRATION-PLAN.md` and in `docs/architecture/ARCH-004.md` ("Open Questions").

## Decision

- [x] **Approved with minor fixes** — the *docs-only* Session 6 PR (ARCH/TEST-SPEC + TC comments) is ready to merge as-is; nothing in it needs to change
- [x] **Needs changes** — Finding 1 is a genuine data-integrity gap in `shared/schema.ts` /
  `server/routes/transactions.ts` that should be fixed (add `.positive()` to `amount` in
  `insertTransactionSchema`) before REQ-004 can be considered reviewed and closed; Finding 2 is
  lower urgency but should be fixed alongside it (add a `.refine()` requiring
  `transferToAccountId` when `type === "transfer"`)

### Notes

- Both decision boxes are deliberately checked, same pattern as CR-001: the documentation PR can
  merge independently of findings that live in code this PR does not touch.
- Recommended fix, when picked up: a single `insertTransactionSchema` change in `shared/schema.ts`
  (`amount: z.number().positive()` + a `.refine()` for the transfer/target-account pairing) fixes
  both findings at once, since both are the same category of missing input validation on the same
  schema. Add regression tests `TC-004-09` ("rejects a transaction with a negative amount") and
  `TC-004-06` ("rejects a transfer with no target account") alongside the fix.
- Unlike CR-001's Finding 1 (an active, exploitable access-control bug), Finding 1 here requires a
  malicious or buggy API caller to submit a negative amount directly — the UI form does not offer
  this input — so it's real but lower exposure than an auth bypass. Still recommended before
  Session 10 given it's a core domain-invariant violation, not scheduled backlog cleanup.
- Once fixed, update this CR's Decision to **Approved**.
