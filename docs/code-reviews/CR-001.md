## Findings

_Both findings are pre-existing behavior in already-shipped code (not introduced by this PR),
surfaced while writing ARCH-015 against REQ-015's ACs. Neither is a regression from Session 5's
own changes — Session 5 changed no application code._

| # | Severity | File / Line | Description |
|---|----------|-------------|-------------|
| 1 | **blocker** | `server/routes/users.ts:84` (`PATCH /:id/password`) | The route has no `requireAdmin` (by design — REQ-015 requires that a regular user can change their own password) but also never checks `req.session.userId === id`. Any authenticated user can currently change **any other user's password** by calling this endpoint with a different user's `id` — `oldPassword` is only checked when the caller chooses to supply it (AC-015-09's admin flow legitimately omits it), so an attacker simply omits it too. Violates REQ-015's own Notes ("a user may only use their own ID") and `security.md`'s Broken Access Control rule ("re-check authorization server-side on every request"). |
| 2 | **major** | `server/routes/users.ts:66-80`, `:110-118`, `:84-106` (`DELETE /:id`, `POST /:id/2fa-reset`, `PATCH /:id/password`) | AC-015-07, AC-015-09, and AC-015-13 all require that deleting a user, resetting their password, or resetting their TOTP invalidates that user's active sessions. No code path touches the session store (`server/session.ts`'s `MemoryStore`) — a user who was just deleted or had their password/TOTP reset by an admin keeps any already-authenticated session until it naturally expires (up to `SESSION_MAX_AGE_HOURS`, default 8h). A deleted user can keep using the app for hours after their account is removed. |

Both findings, plus 6 lower-severity missing-test items, are catalogued in the Test Gap Backlog of
`docs/MIGRATION-PLAN.md` and in `docs/architecture/ARCH-015.md` ("Open Questions").
