# REQ-017 — Automatic Transfer Detection during Import

**Status:** draft
**Created:** 2026-09-25
**Traced by:** ARCH-017, TEST-017

## User Story

As a user importing bank statements from several of my own accounts,
I want transfers between my own accounts to be recognized automatically in the import preview,
in order to avoid classifying them by hand and to prevent a single transfer from being counted
as both an expense and an income.

## Background

A transfer between two own accounts (e.g. N26 → DKB) appears on **both** statements: as a debit
on the source account and as a credit on the target account. Today every parsed row is imported
as `income` or `expense` with `transferToAccountId: null` (REQ-005, REQ-011). The user has to
change transfers by hand after the import, and if both statements are imported, the credit on the
target account inflates income on the dashboard (REQ-007) and in the Sankey diagram (REQ-009).

The data model already supports transfers: `type = "transfer"` plus `transferToAccountId` on the
**source** side (REQ-004, AC-004-05, AC-004-11). The summary counts a transfer once, as an
outgoing flow of the source account and an incoming flow of the target account. The matching
credit on the target statement is therefore redundant and must not be imported as income.

Own accounts can be identified because `accounts.iban` is stored (REQ-002), and most statements
print the counterparty IBAN next to a booking (currently discarded by the N26 and DKB parsers).

Two detection strategies, in order of precedence:

1. **Counterparty IBAN** — the booking's counterparty IBAN equals the IBAN of another own account.
   Deterministic; the target account is known.
2. **Counter-booking match** — no usable IBAN, but an already stored transaction on another own
   account has the same amount, the opposite direction, and a date within the matching window.
   Heuristic; only ever a suggestion.

Detection only pre-fills the import preview. Nothing is changed without the user confirming the
import, and every suggestion can be overridden in the preview.

## Acceptance Criteria

### AC-017-01: Outgoing transfer detected by counterparty IBAN

```gherkin
Given own accounts "N26" and "DKB Giro" exist and "DKB Giro" has the IBAN "DE02120300000000202051"
And a statement for "N26" contains a debit of 500,00 € whose counterparty IBAN is "DE02120300000000202051"
When the user uploads the statement and selects "N26" as the account in the preview
Then the preview row shows "Umbuchung"
And its target account is "DKB Giro"
```

### AC-017-02: Imported outgoing transfer is stored as a transfer

```gherkin
Given the preview row from AC-017-01 is marked as a transfer to "DKB Giro"
When the user clicks "Importieren"
Then the transaction is stored with type "transfer" and transferToAccountId of "DKB Giro"
And it is not counted in the expenses of "N26" in GET /api/summary/:month
```

### AC-017-03: Incoming transfer by counterparty IBAN is marked as counter-booking

```gherkin
Given own accounts "N26" with the IBAN "DE89370400440532013000" and "DKB Giro" exist
And a statement for "DKB Giro" contains a credit of 500,00 € whose counterparty IBAN is "DE89370400440532013000"
When the user uploads the statement and selects "DKB Giro" as the account in the preview
Then the preview row shows "Gegenbuchung von N26"
And the row is excluded from the import by default
```

### AC-017-04: Foreign counterparty IBAN is not treated as a transfer

```gherkin
Given no own account has the IBAN "DE44500105175407324931"
And a statement contains a debit of 80,00 € whose counterparty IBAN is "DE44500105175407324931"
When the user uploads the statement
Then the preview row is an expense
And no target account is set
```

### AC-017-05: Counterparty IBAN of the selected account itself is not a transfer

```gherkin
Given the own account "N26" has the IBAN "DE89370400440532013000"
And a statement contains a booking whose counterparty IBAN is "DE89370400440532013000"
When the user selects "N26" as the account in the preview
Then the preview row is not marked as a transfer
```

### AC-017-06: IBAN comparison ignores spaces and letter case

```gherkin
Given the own account "DKB Giro" has the IBAN "DE02120300000000202051"
And a statement lists the counterparty IBAN as "de02 1203 0000 0000 2020 51"
When the user uploads the statement and selects another own account in the preview
Then the preview row is marked as a transfer to "DKB Giro"
```

### AC-017-07: Incoming credit without IBAN matched against a stored outgoing transfer

```gherkin
Given a stored transaction of type "transfer" from "N26" to "DKB Giro" of 500,00 € dated 2026-09-01
And a statement for "DKB Giro" contains a credit of 500,00 € dated 2026-09-02 without a counterparty IBAN
When the user uploads the statement and selects "DKB Giro" as the account in the preview
Then the preview row is suggested as the counter-booking of that transfer
And the row is excluded from the import by default
```

### AC-017-08: Outgoing debit without IBAN matched against a stored incoming credit

```gherkin
Given a stored income transaction of 300,00 € on "DKB Giro" dated 2026-09-10
And a statement for "N26" contains a debit of 300,00 € dated 2026-09-09 without a counterparty IBAN
When the user uploads the statement and selects "N26" as the account in the preview
Then the preview row shows "Umbuchung" with the target account "DKB Giro"
And the row shows "Ersetzt Einnahme vom 10.09.2026"
```

### AC-017-09: Amount difference or date outside the window prevents a match

```gherkin
Given a stored transaction of type "transfer" from "N26" to "DKB Giro" of 500,00 € dated 2026-09-01
And a statement for "DKB Giro" contains a credit of 500,00 € dated 2026-09-10 without a counterparty IBAN
When the user uploads the statement and selects "DKB Giro" as the account in the preview
Then the preview row is an income
And it is included in the import by default
```

### AC-017-10: Ambiguous match yields no suggestion

```gherkin
Given two stored outgoing transfers of 500,00 € from different own accounts to "DKB Giro" within the matching window
And a statement for "DKB Giro" contains a credit of 500,00 € without a counterparty IBAN
When the user uploads the statement and selects "DKB Giro" as the account in the preview
Then the preview row is an income
And no counter-booking is suggested
```

### AC-017-11: User can override a detected transfer

```gherkin
Given a preview row marked as a transfer to "DKB Giro"
When the user selects "Keine Umbuchung" as the target account and clicks "Importieren"
Then the transaction is stored with type "expense"
And transferToAccountId is null
```

### AC-017-12: User can import a counter-booking anyway

```gherkin
Given a preview row marked as a counter-booking and excluded by default
When the user re-includes the row and clicks "Importieren"
Then the transaction is stored as an income on the selected account
```

### AC-017-13: Detection applies to the Paperless import

```gherkin
Given own accounts "N26" and "DKB Giro" with IBANs exist
And a Paperless document for "N26" contains a debit whose counterparty IBAN is the IBAN of "DKB Giro"
When the user loads the document into the Paperless import preview
Then the preview row is marked as a transfer to "DKB Giro"
```

### AC-017-14: Importing a transfer deletes the stored income it replaces

```gherkin
Given a stored income transaction of 300,00 € on "DKB Giro" dated 2026-09-10
And a preview row for a debit of 300,00 € on "N26" shows "Umbuchung" to "DKB Giro" and "Ersetzt Einnahme vom 10.09.2026"
When the user clicks "Importieren"
Then a transaction of type "transfer" from "N26" to "DKB Giro" of 300,00 € is stored
And the stored income transaction on "DKB Giro" no longer exists
And GET /api/summary/2026-09 counts the 300,00 € as a transfer only, not as income of "DKB Giro"
```

### AC-017-15: Overriding the transfer keeps the stored income

```gherkin
Given a preview row that shows "Umbuchung" to "DKB Giro" and "Ersetzt Einnahme vom 10.09.2026"
When the user selects "Keine Umbuchung" as the target account and clicks "Importieren"
Then the row is stored as an expense on "N26"
And the stored income transaction on "DKB Giro" still exists
```

### AC-017-16: Transfer detected by IBAN also replaces a matching stored income

```gherkin
Given own accounts "N26" and "DKB Giro" exist and "DKB Giro" has the IBAN "DE02120300000000202051"
And a stored income transaction of 500,00 € on "DKB Giro" dated 2026-09-02
And a statement for "N26" contains a debit of 500,00 € dated 2026-09-01 whose counterparty IBAN is "DE02120300000000202051"
When the user uploads the statement and selects "N26" as the account in the preview
Then the preview row shows "Umbuchung" with the target account "DKB Giro"
And the row shows "Ersetzt Einnahme vom 02.09.2026"
```

### AC-017-17: Failed deletion of a replaced income is reported

```gherkin
Given a preview row that shows "Ersetzt Einnahme vom 10.09.2026"
And the server rejects the request that deletes the replaced income transaction
When the user clicks "Importieren"
Then the transfer is stored
And the user sees "Einnahme vom 10.09.2026 konnte nicht entfernt werden"
```

## Notes

- **Parser change (REQ-005):** each parser that can see a counterparty IBAN returns it as an
  optional field on `ParsedTransaction`. Parsers without IBAN information (Trade Republic, generic
  fallback — to be verified against real statements) return none; those rows rely on the
  counter-booking match (AC-017-07/08) only.
- **Account selection:** the parse endpoint does not know which account the statement belongs to
  (the account is chosen in the preview, per row or for all rows). Detection must therefore be
  (re-)evaluated relative to the row's selected account — see AC-017-05.
- **Matching window:** ±3 calendar days between the booking dates of both sides (bank value dates
  differ for SEPA transfers and weekends). Amounts must match to the cent. The exact window is an
  ARCH decision; AC-017-07/09 assume 3 days.
- **Precedence:** IBAN detection wins over the counter-booking match. A counter-booking match is
  only suggested when exactly one candidate exists (AC-017-10) — fail safe, never guess.
- **Counter-bookings are not stored.** The target side of a transfer is represented by the source
  side's `transferToAccountId` (REQ-004 AC-004-11); storing the credit as well would double-count.
- **Replaced income (AC-017-08, 14–17):** when a detected outgoing transfer has exactly one
  stored *income* on the target account with the same amount within the matching window, that
  income is the redundant counter-booking. The preview shows it, and the import deletes it after
  the transfer is saved (decision: ARCH-017 Open Question 1, option b). Several candidates → the
  transfer is still suggested (for the IBAN strategy), but nothing is replaced.
- **Privacy (security.md):** counterparty IBANs are personal data — never logged. Whether they are
  persisted on `transactions` (new nullable column, backwards-compatible `ALTER TABLE`) or only
  used transiently during the preview is an ARCH decision; transient use is preferred (YAGNI).
- **Accounts without IBAN** cannot be detected by strategy 1; strategy 2 still applies.
- **UI labels** (ARCH-017): "Umbuchung" with a target-account select (option "Keine Umbuchung"),
  "Gegenbuchung von <Konto>" for counter-bookings, and "Ersetzt Einnahme vom <TT.MM.JJJJ>" for a
  replaced stored income.
- Related: REQ-002 (account IBAN), REQ-004 (transfer model), REQ-005 (parsers), REQ-006
  (category suggestion), REQ-007/009 (summary, Sankey), REQ-011 (batch import), REQ-016
  (Paperless import).
