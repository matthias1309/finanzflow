# REQ-013 — Two-Factor Authentication Setup (TOTP)

**Status:** approved
**Created:** 2026-04-30
**Traced by:** _(pending ARCH and TEST)_

## User Story

As a user of FinanzFlow,
I want to set up and manage a second factor (TOTP),
in order to keep my account protected even if my password is compromised.

## Background

TOTP (Time-based One-Time Password, RFC 6238) generates a 6-digit code every 30 seconds in an
authenticator app (Google Authenticator, Authy, 1Password, etc.). Each user sets up their own
TOTP. The setup flow is triggered on first login when no TOTP is set up yet — right after the
password check, before the user reaches the Dashboard.

**8 one-time recovery codes** are shown right after setup — exactly once. Each code can be used
only once for a login. New codes can be generated from the Dashboard (this invalidates all old
codes).

**Emergency reset via CLI:** If neither TOTP nor recovery codes are available, 2FA can be reset via
a server command. The command expects `--user <username>` to specify the affected user.

**Admin reset via UI:** An admin can reset any user's TOTP via the user management page (see
REQ-015).

**Environment variables:**

| Variable | Purpose | Example |
|---|---|---|
| `TOTP_ISSUER` | Name shown in the authenticator app | `FinanzFlow` |
| `SESSION_MAX_AGE_HOURS` | Session duration in hours | `8` |

## Acceptance Criteria

### AC-013-01: User is redirected to setup after password login if 2FA is not set up

```gherkin
Given the user has entered username and password correctly
And 2FA is not yet configured for this user
Then the user is redirected directly to the TOTP setup flow
And can only reach the Dashboard after completing setup
```

### AC-013-02: Setup flow — QR code is shown

```gherkin
Given the user clicks "2FA jetzt einrichten"
Then a setup dialog opens
And a QR code is shown that can be scanned with an authenticator app
And the manual entry key (Base32) is also visible
```

### AC-013-03: Setup verification succeeds

```gherkin
Given the user has scanned the QR code with their authenticator app
When the user enters a valid 6-digit TOTP code and confirms
Then 2FA is activated
And 8 recovery codes are shown
And a notice explains that these codes are shown only once
```

### AC-013-04: Setup verification fails

```gherkin
Given the user has scanned the QR code
When the user enters a wrong 6-digit code
Then the setup dialog stays open
And an error message "Ungültiger Code — bitte erneut versuchen" is shown
And 2FA is not activated
```

### AC-013-05: Recovery codes are shown only once

```gherkin
Given 2FA was just set up successfully
And the recovery codes were shown
When the user closes the dialog and reopens it
Then the recovery codes are no longer visible
And only the count of remaining codes is shown
```

### AC-013-06: Regenerate recovery codes

```gherkin
Given the user is logged in and 2FA is active
When the user clicks "Recovery-Codes neu generieren" in the Dashboard
And confirms the action in a confirmation dialog
Then 8 new recovery codes are shown
And all old recovery codes are permanently invalid
```

### AC-013-07: Reset 2FA via CLI

```gherkin
Given the user "admin" no longer has access to TOTP and all recovery codes are used up
When the server command "npm run 2fa:reset -- --user admin" is run on the server
Then 2FA is disabled for "admin" and the TOTP secret is deleted
And on the next login attempt, the password alone is sufficient
And the user is redirected directly to the TOTP setup flow after the password login
```

## Notes

- The TOTP secret is stored encrypted per user in the `users` table (AES-256, key via environment
  variable `TOTP_ENCRYPTION_KEY`).
- Recovery codes are stored as bcrypt hashes — never in plaintext.
- Time window for TOTP validation: ±1 step (±30 s) to tolerate clock drift on client or server.
- Each TOTP code may only be accepted once per 30-second window (replay protection via a
  last-used timestamp in the DB).
- The setup flow is only accessible once the user has already completed password authentication.
- `npm run 2fa:reset -- --user <username>` is a separate script (`script/reset2fa.ts`) that writes
  directly to the DB — not an API endpoint. If `--user` is missing, the script prints an error
  message with usage instructions.
