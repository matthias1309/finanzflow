# REQ-016 — Paperless Bank Statement Import

**Status:** approved
**Created:** 2026-09-23
**Traced by:** _(pending ARCH and TEST)_

## User Story

As a user,
I want bank statements I have already archived in Paperless-ngx to be read directly into
FinanzFlow,
so that I don't have to additionally download and upload them manually.

## Background

FinanzFlow can already process PDF bank statements manually (REQ-005): upload → bank-specific
parser (`server/pdfParser.ts`) → preview → confirmation. Paperless-ngx runs on the same Raspberry
Pi and already archives the same bank statements as PDF, tagged with `Kontoauszug` plus a second
tag that names the account (`Autokonto`, `Tagesgeldkonto`, `Essenskonto`, …).

This feature adds a second PDF source — the Paperless REST API — in front of the same parsing
pipeline. The existing parser, preview, and confirmation flow from REQ-005 are reused, not
duplicated.

### Data Model

**New table `paperless_account_mappings`** — maps a Paperless tag to a FinanzFlow account:

| Field | Type | Description |
|---|---|---|
| `id` | integer, PK | — |
| `paperlessTag` | text, unique | Second tag in Paperless, e.g. `"Essenskonto"` |
| `accountId` | integer, FK → `accounts.id` | Associated FinanzFlow account |

**New table `paperless_imports`** — prevents double-importing on repeated sync runs:

| Field | Type | Description |
|---|---|---|
| `id` | integer, PK | — |
| `paperlessDocumentId` | integer, unique | Document ID from Paperless |
| `accountId` | integer, FK → `accounts.id` | Account the import was assigned to |
| `importedAt` | text (ISO timestamp) | Time of the import |

### Configuration

New environment variables (analogous to existing secrets in `.env`):

| Variable | Description |
|---|---|
| `PAPERLESS_BASE_URL` | e.g. `http://localhost:8000` (same Docker network on the Pi) |
| `PAPERLESS_API_TOKEN` | Paperless API token, never visible to the client |

## Acceptance Criteria

### AC-016-01: Create a mapping between a Paperless tag and an account

```gherkin
Given the user is on the "Paperless-Einstellungen" page
When the user maps the Paperless tag "Essenskonto" to the account "Gemeinschaftskonto"
And clicks "Speichern"
Then a new entry is saved in paperless_account_mappings
And the tag "Essenskonto" appears in the mapping overview with its associated account
```

### AC-016-02: Edit an existing mapping

```gherkin
Given the tag "Autokonto" is currently mapped to the account "Girokonto"
When the user changes the mapping to the account "Auto & Verkehr"
Then the existing entry in paperless_account_mappings is updated
And future imports with tag "Autokonto" use the new account
```

### AC-016-03: Show open Paperless documents

```gherkin
Given 5 documents with tag "Kontoauszug" exist in Paperless
And 3 of them are already recorded in paperless_imports
When the user opens the "Aus Paperless importieren" page
Then the system shows only the 2 not-yet-imported documents
And each document shows file name, Paperless creation date, and the detected second tag
```

### AC-016-04: Automatically assign a document with an unambiguous account tag

```gherkin
Given an open Paperless document carries the tags "Kontoauszug" and "Essenskonto"
And "Essenskonto" is mapped to the account "Gemeinschaftskonto"
When the user selects the document for import
Then the account "Gemeinschaftskonto" is automatically pre-selected
And the user does not need to choose the account manually
```

### AC-016-05: Document without a mapped account tag shows a notice

```gherkin
Given an open Paperless document carries only the tag "Kontoauszug" without a further account tag
When the user views the list of open documents
Then the document is marked with the notice "Kein Konto zugeordnet"
And the user can select the account manually before importing
```

### AC-016-06: Document with multiple account tags shows a notice

```gherkin
Given an open Paperless document carries the tags "Kontoauszug", "Autokonto", and "Essenskonto"
When the user views the list of open documents
Then the document is marked with the notice "Mehrdeutige Zuordnung"
And no account is auto-selected
And the user must select the account manually before importing
```

### AC-016-07: Load and parse a document from Paperless

```gherkin
Given the user has selected a Paperless document with a detected account
When the user clicks "Importieren"
Then the system downloads the PDF via the Paperless API
And the PDF goes through the same parsing pipeline as in REQ-005 (bank detection, transaction extraction)
And a preview table shows the detected transactions for confirmation
```

### AC-016-08: Confirm the import and mark the document as imported

```gherkin
Given the preview shows 12 transactions parsed from a Paperless document
When the user confirms the transactions
Then all 12 transactions are saved to the associated account
And an entry with the Paperless document ID is created in paperless_imports
And the document no longer appears in the list of open documents on future queries
```

### AC-016-09: Paperless is unreachable

```gherkin
Given PAPERLESS_BASE_URL is configured, but Paperless does not respond
When the user opens the "Aus Paperless importieren" page
Then the system shows an error message "Paperless ist nicht erreichbar"
And the manual PDF upload feature from REQ-005 remains usable unchanged
```

### AC-016-10: Invalid or missing API token

```gherkin
Given PAPERLESS_API_TOKEN is not set or rejected by Paperless
When the system tries to query documents
Then an error "Paperless-Zugriff nicht autorisiert" is shown
And no documents are displayed
```

## Notes

- Reuse: `parsePDF()` from `server/pdfParser.ts` stays unchanged — Paperless only supplies the PDF
  buffer as an additional source instead of the Multer upload. Bank detection, transaction
  extraction, duplicate detection within a single import, and category suggestions (REQ-006)
  apply identically.
- New endpoint `server/routes/paperless.ts`:
  - `GET /api/paperless/documents` — open documents including detected/ambiguous/missing account tag
  - `POST /api/paperless/documents/:id/import` — downloads, parses, returns a preview (same
    response shape as `POST /api/import/pdf`)
  - `POST /api/paperless/documents/:id/confirm` — only creates the `paperless_imports` entry
    (marks the document as imported); the actual saving of transactions runs client-side through
    the existing endpoints `POST /api/transactions/batch` and `POST /api/category-rules/learn` —
    no duplication of the persistence logic from REQ-005
  - `GET /api/paperless/mappings`, `POST /api/paperless/mappings`, `PUT /api/paperless/mappings/:id`,
    `DELETE /api/paperless/mappings/:id` — management of `paperless_account_mappings`
- Tag evaluation ("second tag ≠ Kontoauszug") happens server-side based on the tag list Paperless
  returns per document, not by string-matching on file names.
- No auto-matching by name similarity between Paperless tag and account name — the mapping is
  established exclusively and explicitly via `paperless_account_mappings`, to avoid
  misassignments for similarly named accounts.
- No automatic background sync in this version — the import is triggered manually via the UI (see
  the risk note below for a later extension).
- `PAPERLESS_API_TOKEN` is used server-side and never exposed to the client (analogous to existing
  server secrets).
- Open for a later version: automatic cron-job sync with notification on new documents —
  intentionally not part of this REQ, since error handling without UI interaction needs additional
  design work.
